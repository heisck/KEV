# Deploying KEV to Render

Two services from this one repo: **`kev-backend`** (Spring Boot) and **`kev-ml`** (FastAPI +
InsightFace). Both ship as Docker images. Postgres stays on **Neon** and Redis on **Upstash** —
Render only runs the two app containers.

The frontend is an Expo app; it is **not** deployed here (it builds through EAS and just points
at the backend's public URL).

---

## 1. Answers to the obvious questions

**Do I link the whole GitHub repo?**
Yes — link `heisck/KEV` once. Render reads [`render.yaml`](../render.yaml) at the root and
creates both services from it, each with its own build context (`./backend`, `./ml`). You do
not split the monorepo.

**What are my start commands?**
None to type. Both services are `runtime: docker`, so the start command is the `CMD` inside
each Dockerfile:

| Service       | Effective start command                              |
| ------------- | ---------------------------------------------------- |
| `kev-backend` | `java -jar app.jar --server.port=$PORT`               |
| `kev-ml`      | `uvicorn app.main:app --host 0.0.0.0 --port $PORT`    |

Leave Render's "Start Command" field **empty**. Java has no native runtime on Render, so Docker
is the only option for the backend anyway.

**Does the ML service live on Render too?**
Yes — as its own web service, and the backend reaches it over Render's private network, so it
never takes a public hop. The `buffalo_sc` model is baked into the image at build time
(`ml/Dockerfile`), so a restart does not re-download it.

## 2. Before you touch Render

1. **Neon** — create the project in **eu-central-1** (Frankfurt) and copy the **pooled**
   connection string (host must contain `-pooler`).
2. **Upstash** — create the Redis database in the same region. Copy the bare host (from the
   `redis://` string, *not* the REST URL), the port, and the token.
3. **Gmail refresh token** — `node scripts/gmail-refresh-token.mjs`. Render blocks outbound
   SMTP ports, which is why email goes over the Gmail REST API.
4. Have your Google OAuth client IDs and Sentry DSNs to hand.

Full variable reference: [ENVIRONMENT.md](./ENVIRONMENT.md).

---

## 3. Deploy

1. Push `render.yaml`, `backend/Dockerfile` and the rest of `main` to GitHub.
2. Render dashboard → **New → Blueprint** → pick the `KEV` repo → Render finds `render.yaml`.
3. Render lists every `sync: false` variable and asks for a value. Fill in:

   | Variable                                                       | Value                                              |
   | -------------------------------------------------------------- | -------------------------------------------------- |
   | `SPRING_DATASOURCE_URL`                                          | Neon pooled JDBC URL (`jdbc:postgresql://…?sslmode=require`) |
   | `SPRING_DATASOURCE_USERNAME` / `SPRING_DATASOURCE_PASSWORD`      | Neon credentials                                    |
   | `UPSTASH_REDIS_HOST` / `UPSTASH_REDIS_PASSWORD`                  | Upstash host + token                                |
   | `GOOGLE_CLIENT_IDS`                                              | comma-separated web + iOS client IDs                |
   | `APP_CORS_ALLOWED_ORIGINS`                                       | your app origins (see step 6)                       |
   | `KEV_ADMIN_EMAIL` / `KEV_ADMIN_PASSWORD` / `KEV_ADMIN_NAME`      | first admin — password ≥ 12 chars                   |
   | `SENTRY_DSN_BACKEND`, `ML_SENTRY_DSN`, `HF_TOKEN`, Gmail, Arkesel | as applicable; blank keeps them log-only            |

   `JWT_SECRET` is generated by Render (`generateValue: true`) — don't set it by hand.
4. **Apply**. First build takes ~5–8 min (Maven downloads, then the ML image bakes the model).
5. Open **kev-ml → Internal Address**. It should read `kev-ml:8000`. If it differs, correct
   `ML_BASE_URL` on `kev-backend` to match and redeploy.
6. Copy the backend's public URL (`https://kev-backend.onrender.com`) and:
   - set `EXPO_PUBLIC_API_URL` to it in the app's build env,
   - add the app's origins to `APP_CORS_ALLOWED_ORIGINS`.
7. Once you can sign in as the admin, **blank out `KEV_ADMIN_PASSWORD`** and redeploy. The
   account is never re-hashed, so leaving the password in the environment buys nothing.

## 4. Verify

```bash
curl https://kev-backend.onrender.com/actuator/health   # {"status":"UP"}
curl https://kev-ml.onrender.com/health                 # {"status":"ok","service":"kev-ml"}
```

If health is `DOWN`, check the backend logs for Flyway (migrations run at boot against Neon)
or Redis. To run without Redis, set `CACHE_TYPE=none`, `MANAGEMENT_HEALTH_REDIS=false` and
clear the Upstash variables.

---

## 5. Things that will bite you

- **Free plan sleeps after 15 min of inactivity.** The wake-up reloads the face model, so the
  first scan of an exam would block for tens of seconds. Both services are on `starter` in the
  blueprint for that reason — dropping `kev-ml` to free is a bad trade during an exam.
- **512 MB is not enough for `kev-ml`.** onnxruntime plus the model exceeds it; the container
  gets OOM-killed mid-request. Keep it at `starter` or higher.
- **`ML_READ_TIMEOUT_SECONDS` (default 120)** covers roster embedding backfills, which fetch
  every student photo over the UITS link. Don't lower it because a single scan is fast.
- **Region matters.** Backend, ML, Neon and Upstash all in Frankfurt; a database in Oregon adds
  a transatlantic round trip to every query.
- **Logs.** The container's disk is ephemeral — `logs/kev-backend.log` does not survive a
  restart. Sentry and Render's log stream are the durable copies.
